# 从精彩演示到可信实验

当前结果证明内置测试和实现闭环能运行，**不证明 TRACE 改善了真实项目交付**。不要把内置三场景的 3/3 变异检出率描述成行业领先或生产安全率。

## 下一步实验设计

选择至少 10 个独立小需求，由独立审阅者确认业务契约。保留一组修复过程不可见的评估用例。可以在实验前固定用例与评分规则的版本哈希，减少事后调整评价标准。

在相同模型、温度、工具与 token 预算下比较：

| 条件 | 修复时反馈 | 提交标准 |
| --- | --- | --- |
| A | 需求文本 | Agent 自报完成 |
| B | 需求文本和固定测试 | 固定测试通过 |
| C | 需求文本、固定测试与变异反馈 | 测试通过、预设变异被检出、人工审阅 |

每个需求至少重复三次，记录随机因素。相同任务在不同条件间的顺序应随机化；不要让后一组直接继承前一组修复结果。模型失败、超时和预算耗尽也必须计入。

## 指标定义

- 未公开用例通过率：通过的独立评估断言数 / 总评估断言数。
- 漏验需求数：人工审阅确认未满足、但流程曾接受的需求数量。
- 变异检出率：被测试区分出的有效非等价变异 / 有效变异总数。
- 验收耗时：从收到交付物到审阅者完成接受或拒绝的时间。
- 工具与模型成本：实际请求次数、提供方返回的 token 使用、执行时间；没有真实值时留空，不估造。
- 人工修复次数：流程结束后还需要人工修改的次数。

## 需要排除的干扰

不能只选自己已经知道补丁的题。变异可能不改变可观察行为，需要人工剔除等价变异。修复模型不能随意修改评分标准；生成测试的模型也不能成为唯一评判者。样本很少时应报告逐项结果，不用夸大的百分比代替证据。

## 为什么当前仍然有价值

先验证系统机制：冻结契约、独立执行、失败反馈、反事实检查、持久记录和人工关卡。再通过独立实验评估这些机制带来的实际效果。
